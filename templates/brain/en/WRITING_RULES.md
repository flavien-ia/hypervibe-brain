# Writing in the brain: the rules

To read before any writing in the vault, by an AI as by {{NAME}}. One page, on purpose. The detail (the types, the fields) is in [`vault/CLAUDE.md`](vault/CLAUDE.md). The capture skills point here instead of copying these rules: any new rule is added here, and only here. This file belongs to {{NAME}}, who may change it.

1. **Search before writing.** If a note already covers the subject, enrich it (with {{NAME}}'s agreement if it is `trusted`); do not create a second one.
2. **One note = one thing**, with a title that says the thing itself. Two subjects, two notes.
3. **One decision = its own note**: a `note` of nature `decision`, short, titled with the decision itself, linked to the project it comes from. Never only a line inside a project note. A lesson (a working rule, a trap) is a note of nature `lesson`, a client's feedback a note of nature `feedback`.
4. **Routing.** A note carries what one needs to know to think about the subject, not the data itself. It says **where it comes from** (`source`: its provenance) and **where the data lives** when there is some (`data`: the addresses in a database, an accounting app, a CRM, which `brain_fetch` reads). Never copy what moves (amounts, metrics, statuses) nor a heavy document: point to it. A provenance may become historical (an archived file, a conversation) without being a fault; the addresses in `data` are the ones checked, and a document or a folder goes there too (`dropbox://`, `dev://`, spaces written `%20`). A self-standing note (a lesson, a concept, a decision) only needs its provenance.
5. **Links that say why.** 5 to 10 `[[slug]]` per note, only meaningful ones, preferably inside a sentence that says the relation, not a closing "See [[x]]": that sentence is what the AI reads to decide whether to follow the link.
6. **The type makes the folder**, the file name is a lowercase ASCII slug with dashes; one or two domains from the list in `brain.json`, never none.
7. **The machine creates; on a validated note it only adds.** What it writes is born a `seed`, with a `source`. On a `trusted` note it never rewrites {{NAME}}'s text: it may only add a fact that says where it comes from (the note's `updated` takes today's date) and keep its own machine zones up to date. On a validated concept or idea, or a validated note of nature `decision` or `lesson`, which is {{NAME}}'s thinking, it adds nothing: it proposes the change in the weekly letter. An `archived` note takes no new fact. Any other change to a `trusted` note needs {{NAME}}'s agreement. A fact that contradicts what the note says (a duration, a price, a date, a state, a decision) says so explicitly: what changes, from when, where it comes from, and what the note said before; on a validated decision or lesson, it is only a proposal of the letter.
8. **What is outdated or closed.** A replaced note is merged into the new one (what only it carried moves over) then deleted, with {{NAME}}'s agreement; a closed note (an abandoned project, a discarded idea) becomes `archived`, never deleted: it stays findable but no longer pushes forward. Deleting or merging a note born from a source requires linking its item to the kept note in `sources/<source>/seen.json`, or the source creates it again.
9. **What never goes in**: a secret (key, password, `.env`), a task or a passing reminder ("will anyone want this in six months?"), third-party data marked `public`.
10. **Write for the next agent**: clear sentences, accurate frontmatter.
